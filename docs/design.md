기준일: 2026-10-22

## 2. 서비스 범위

### 확정된 초기 요구사항

- 교회 공동체 구성원의 일반 로그인 및 소셜 로그인.
- 사용자 프로필, 평신도·목회자 구분, 셀 소속과 역할 관리.
- 목회자 직책과 목회 사역 부서 관리.
- 셀 소속에 따른 기도 게시판 접근, 기도글 작성, 댓글 및 익명 댓글.
- 기도글의 “기도했습니다” 토글 반응.
- 목회자의 사용자 대상 달란트 지급과 적립 내역 관리.

### 후속 범위

- 얼굴 인식 출석 체크.
- 사역팀 소속, 복수 사역팀 가입 및 사역팀 기도 게시판.
- 사용자 그룹 생성.

현재 그룹 테이블 이름은 사용자의 후속 요청에 따라 `cell`로 한다.
사역팀·사용자 생성 그룹은 기존 backlog로 남기되 현재 셀 스키마에 선반영하지 않는다.
회장단·사역팀 팀장 등의 역할은 초기 구상에 포함되었지만 상세 권한은 미결정이다.

## 3. 아키텍처와 기술 방향

### 확정

| 영역 | 방향 |
| --- | --- |
| 아키텍처 | 기능별로 구분하는 모듈형 모놀리스 |
| 언어·프레임워크 | Java 21, Spring Boot 4.1.1, Spring Web MVC |
| 데이터 접근 | Spring Data JPA, Hibernate, PostgreSQL |
| 스키마 관리 | Flyway |

| API 문서 | springdoc-openapi 3.x 안정 패치 |
| 빌드·테스트 | Gradle 9.8.x, JUnit, Testcontainers |
| 의존성 관리 | Boot가 관리하는 라이브러리는 BOM 버전 사용 |
| 프런트엔드 | Next.js 16, Vercel; 모바일 앱은 Capacitor 방향 |

| 향후 호스팅 | AWS App Runner는 추후 검토 |

이 버전 목록은 선정 기록이며 최신 버전이라는 의미가 아니다. 현재 적용 버전은 빌드 파일과 README에서 확인한다.

### 패키지 구성 제안

단일 Gradle 프로젝트를 유지하며 아래 기능 경계로 시작한다. 아직 생성된 패키지 목록은 아니다.

```text
com.ubique.prayer
├── auth       # 로그인 수단, 인증, 토큰 갱신
├── member     # 사용자, 목회자 정보, 역할
├── cell       # 셀, 소속 관리
├── prayer     # 기도글, 댓글, 반응
├── talent     # 달란트 지급 내역
├── storage    # R2 업로드 및 파일 메타데이터
├── config     # 공통 설정
└── common     # 실제 공유가 필요한 타입과 예외
```

필요한 계층을 각 기능 내부에 둔다. 다른 기능의 Repository를 직접 사용하는 범위와 공개 서비스 경계는 구현 시 정한다.

## 4. 사용자·목회자·셀 요구사항

### 확정

- 사용자는 평신도 또는 목회자로 구분한다.
- 평신도는 새신자 그룹 또는 일반 셀 중 정확히 하나에 소속된다.
- 평신도는 셀 리더 또는 셀 부리더 직책을 맡을 수 있다. 일반 구성원도 존재한다.
- 목회자 상세 정보는 사용자와 분리한 테이블에 사용자 FK, 목회자 직책, 사역 부서를 둔다.
- 직책은 담임목사·목사·전도사 등을 표현하고, 사역 부서는 청년부·유아부 등으로 확장할 수 있어야 한다.
- 프로필에는 이름, 이메일, 생년월일, 프로필 이미지, 재적에 따른 상태, 가입·수정 시각, 역할, 셀 소속을 제공한다.
- 사용자 테이블에 이메일 인증 완료 시각은 두지 않는다.
- 셀은 새신자와 일반 셀을 구분한다. 일반 셀 분류는 `S/A/B/C`를 사용한다.
- 셀 이름, 소개, 상태, 생성·수정 시각을 관리한다.
- 목회자의 셀 소속은 선택이다. 상세 필드는 [DB 명세](database.md)를 따른다.

### 미결정

- 소셜 제공자가 이메일·생년월일을 주지 않는 경우 가입 완료까지의 입력 흐름.
- 가입 직후 셀 배정 방식과 셀 이동·비활성화 시 처리.
- 목회자 프로필과 사용자 구분 값의 일관성을 보장하는 방법.
- 역할 부여·회수 권한. 리더·부리더는 `user_roles`에서 관리하며 셀별 활성 역할은 각각 최대 1명으로 상세 명세에 정리했다.

## 5. 인증 설계

### 확정

| 항목 | 결정 |
| --- | --- |
| 로그인 수단 | 아이디·비밀번호 로그인과 OAuth 소셜 로그인 지원 |
| Access Token | 클라이언트 메모리에 보관 |
| Refresh Token 클라이언트 저장 | HttpOnly 쿠키 |
| Refresh Token 서버 저장 | PostgreSQL에 해시 저장 |
| Spring Security | `STATELESS` |

비밀번호 로그인 전용 정보와 소셜 제공자 계정 연결 정보를 구분한다.
서비스의 Refresh Token은 일반·소셜 로그인 모두에서 사용할 공통 로그인 유지 정보다.
소셜 제공자가 발급한 토큰과 우리 서비스가 발급한 토큰은 별개의 데이터다.
`STATELESS`는 서비스 Refresh Token 해시를 DB에 저장하지 않는다는 뜻이 아니다.

### 상세 명세 참조

인증 테이블은 `auth_credentials`, `social_accounts`, `refresh_tokens`로 구분한다.
소셜 전용 사용자는 비밀번호 인증 행이 없어도 되고, 일반·소셜 로그인은 공통 토큰 관리 방식을 사용한다.
테이블별 필드와 제약, 로그인·재발급 흐름은 [DB 상세 명세](database.md)에 기록한다.

재발급은 인증 수단 테이블을 다시 조회하지 않고 Refresh Token과 사용자 상태를 확인한다.
SHA-256 해시 저장, Rotation, Token Family 재사용 탐지 및 원자적 교체를 상세 명세에 반영했다.
14일 유효기간은 권장값이며, 쿠키·CSRF 정책과 비밀번호 변경 시 세션 처리 등 남은 결정은 상세 명세의 검토 항목을 따른다.

## 6. 역할과 기도 기능

### 확정

- 역할을 테이블로 관리한다.
- 목회자는 관리자로서 모든 사용자의 기도글을 읽을 수 있다.
- 기존 요구사항은 목회자의 기도글 수정·삭제 및 작성을 허용한다. 새 상세 명세의 작성자 전용 삭제 정책과 충돌하므로 [DB 명세의 충돌 항목](database.md#해결이-필요한-충돌)에서 별도 관리한다.
- 사용자 셀 소속에 따라 해당 셀의 기도 게시판에 접근하게 한다.
- 기도글에 “기도했습니다” 반응을 토글할 수 있다.
- 일반 댓글과 익명 댓글을 지원한다.
- 목회자 권한을 가진 사용자가 특정 사용자에게 달란트를 지급할 수 있다.

### 상세 정책과 검토 항목

기본 역할과 셀 역할, 공개 범위, 셀 이동 시 게시글 소속 유지, 익명 댓글과 반응, Soft Delete 정책은
[DB 상세 명세](database.md)를 따른다. 목회자 삭제 권한 충돌, 관리자 익명 작성자 열람 범위와 감사 기록은 아직 해결해야 한다.
달란트는 기존 기능 요구사항으로 유지하되, 이번 11개 테이블에는 포함되지 않았다. 지급 내역·취소·중복 지급 방지 정책의 별도 설계가 필요하다.

## 7. DB 상세 명세의 위치

[docs/database.md](database.md)에서 현재 11개 테이블의 필드명, PostgreSQL 타입, 필수 여부, 설명, 관계와 제약을 관리한다.
필드 정의를 이 문서에 중복하지 않는다. 달란트와 파일 메타데이터는 별도 설계 대상이므로 11개를 서비스 전체 테이블 수로 해석하지 않는다.
상세 명세는 아직 실행 가능한 SQL이 아니다. 구현 시 Flyway 마이그레이션과 Entity의 일치 여부를 검증한다.

## 8. 파일 업로드

### 확정된 아키텍처 흐름

1. 클라이언트가 백엔드에 업로드 URL을 요청한다.
2. 백엔드가 권한을 확인하고 R2용 Presigned URL을 발급한다.
3. 클라이언트가 해당 URL로 R2에 파일을 직접 업로드한다.
4. 클라이언트가 백엔드에 완료를 알리고, 백엔드가 object key 등의 메타데이터를 DB에 저장한다.

프로필 이미지·기도 첨부파일의 저장 데이터와 DB 메타데이터를 구분한다.
업로드 완료 검증, 파일 크기·형식 제한, 다운로드 권한과 미완료 객체 정리 정책은 미결정이다.

## 9. 현재 구현 상태와 후속 작업

기준일의 `codex/backend-environment-setup`에는 Spring Boot, DB 연결, Flyway 설정, 초기 보안 정책,
OpenAPI, Docker Compose, Testcontainers 테스트 및 CI 설정이 있다.
업무 Entity·Repository·API, 업무 마이그레이션 SQL, 실제 로그인·토큰 갱신, R2 연동은 아직 없다.
Render 등 외부 서비스의 실제 연결·배포 완료 여부는 저장소 설정만으로 확인하지 않았다.

후속 작업 순서 제안:

1. DB 상세 명세에 표시한 삭제 권한 충돌과 미결정 정책을 해결한다.
2. DB 상세 명세의 제약조건을 구현 가능한 형태로 구체화하고 최초 Flyway 마이그레이션을 작성한다.
3. 기능별 패키지와 인증을 구현하고 권한·토큰 동작을 테스트한다.
4. 사용자·셀·기도 기능을 구현하고 달란트와 파일 연동을 이어간다.
5. 실제 배포 환경의 도메인·쿠키·CORS 설정과 배포 연결을 검증한다.

DB 상세 명세와 인증 데이터 흐름은 [database.md](database.md)에서 관리한다.
팀원이 변경 이유를 추적할 수 있도록 결정 상태 변경과 관련 코드·SQL을 같은 커밋 또는 PR에서 관리한다.
